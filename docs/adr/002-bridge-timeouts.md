# ADR 2: Timeout-bounded bridge calls, client-side only

**Status:** Accepted
**Date:** 2026-07-30

## Context

The planned `pitaka-bridge` client wraps each H5-to-native call in a promise keyed by a correlation `id`. Nothing in that shape obliges a native handler to reply.

In the production super-app H5 I maintained, the bridge had no timeouts at all. A handler that returned without invoking its callback left the promise pending forever: the page held a loading skeleton indefinitely, with nothing in the logs to explain it and no way for the user to retry. Timeouts existed only at the HTTP layer, below the layer that actually hung.

## Decision

Every call carries a deadline. 10s by default, 120s for interactive methods (`payments.requestPayment`, `ui.confirm`) where a human is deciding. On expiry the client rejects with `TIMEOUT` and evicts the pending entry.

The timeout is client-side only and doesn't cancel native work. `TIMEOUT` means the H5 stopped waiting, not that nothing happened; native may still be showing a confirmation sheet the user goes on to approve. Two rules make that safe: a late response for an evicted `id` is dropped rather than resolving a stale promise, and recovery on a payment is to re-call with the identical `idempotencyKey`, never to show failure or mint a new key.

That retry works because replay is already a ledger property. `applyTransfer` in `src/domain/transfer.ts` derives `txId` from the idempotency key, so a replay returns the original `txId` and writes nothing; the same key with a different amount returns `IDEMPOTENCY_KEY_REUSED` instead of a stale receipt. Note the current check compares only the debit amount, so the same key and amount against a different recipient still reads as a replay. A gap worth closing when the BFF lands.

## Consequences

A slow-but-successful handler now surfaces as `TIMEOUT`, so the H5 shows an indeterminate "checking your payment" state where it could have rendered a receipt. The idempotency key must be generated by the H5 before the first attempt and survive the timeout, which pushes retry correctness onto callers. Every new method must declare an interactivity class. The readiness probe in ADR 3 is the one deliberate exception: it uses a 3 s deadline because its job is to fail fast when there's no host at all.

## When this would change

- Native gains an acknowledged `payments.cancel(id)`: expiry becomes a real cancel with `USER_CANCELLED` semantics.
- Measured on-device p99 for `payments.requestPayment` exceeds 90s: raise the interactive ceiling rather than time out real approvals.
- A method needs genuinely unbounded duration (document capture, upload): it moves to a start-plus-event pattern on the event channel instead of a longer timeout.
- A non-idempotent method is added: it gets a key, or it gets no retry-on-timeout recovery.
